# 性能测试报告

> 2026-10-21 随 UI 改版重写。旧版本报告的「帧耗 p95≈17.8ms」经核实**测的不是应用开销**（见 §1），本文改用主线程任务耗时，并给出改版前后同口径对比。

## 1. 旧测量方法的问题

旧用例（阶段8）用 `requestAnimationFrame` 间隔当「帧耗」，拖拽用页面内合成的 `pointermove`。复查发现两个问题：

1. **测到的是浏览器帧时钟**：在同一 Chromium（headless，`--disable-frame-rate-limit --disable-gpu-vsync`）里打开**空白页**，rAF 间隔同样是 p50 17.8ms / p95 17.9ms——与 500 节点大图的结果几乎相同。也就是说这个数字反映的是无头浏览器固定的出帧节奏，而不是我们每帧做了多少工作；p95 贴着 20ms 阈值，阈值判定基本是噪声。
2. **合成事件没有真正拖动节点**：React Flow 的节点拖拽由 d3-drag 监听真实指针事件，`document.dispatchEvent(new PointerEvent('pointermove'))` 不会触发它，所以「拖拽 p95 0.3–0.7ms」测的是空闲帧。

## 2. 新方法

- **真实拖动**：Playwright `page.mouse.down/move/up` 驱动（走 CDP 输入，和真人操作同一路径），在 500 节点 + 800 边的压测文档上拖第一个节点 40 步。
- **测主线程**：拖动期间用 CDP `Tracing` 采集渲染主线程（`CrRendererMain`）的每个 `RunTask`，统计任务耗时分布与总忙碌时长。
- **判据**：单个任务 >50ms 即 W3C「长任务」，会造成可感知卡顿。断言局部视口拖拽的任务 p95 < 50ms；全览场景只记录。
- 实现：`e2e/perf.ts`（`traceMainThread`）+ `e2e/stage8.spec.ts`。

压测文档：`window.__ds.genDoc(500, 800)`（网格摆放 + 跳跃连线）。生产构建（`pnpm build:e2e` + `vite preview`），1440×900，Playwright 自带 Chromium，软件渲染（容器无 GPU）。Trace 本身有开销，绝对值偏保守，**前后对比用同一方法同一机器顺序执行**。

## 3. 结果（2026-10-21 实测，各 3 次）

### 局部视口（zoom=1，典型编辑场景）

| 版本 | 主线程忙碌（40 步） | 每步 | 任务 p95 | 最长任务 |
| --- | --- | --- | --- | --- |
| 改版前（`main` e674d6b） | 1991–2136ms | ≈51ms | 15.9–17.5ms | 52–72ms |
| 改版后 | 1543–1825ms | ≈41ms | 12.1–13.9ms | 66–101ms |

### 全览（zoom=0.3，500 节点全部可见，最坏场景）

| 版本 | 主线程忙碌（40 步） | 每步 | 任务 p95 | 最长任务 |
| --- | --- | --- | --- | --- |
| 改版前 | 15366–15654ms | ≈389ms | 34.8–36.1ms | 537–563ms |
| 改版后 | 5360–5634ms | ≈137ms | 34.6–36.4ms | 153–161ms |

结论：局部视口忙碌时间约 **−20%**，全览约 **−65%**，全览最长任务从 ~560ms 降到 ~160ms。

## 4. 做了哪些优化

| 发现 | 处理 |
| --- | --- |
| React Flow 的 `EdgeLabelRenderer` 在每次 store 更新时都要 `querySelector` 一次；旧实现每条边都挂一个（即使没有标注），800 条边 = 每帧 800 次 DOM 查询（CPU profile 中占比第一） | 只给**有标注或正在编辑标注**的连线挂载（`DsEdge.tsx`） |
| 改版初稿给节点包装元素加了 transform 入场动画、给节点加了 CSS `drop-shadow` | 实测二者都会让拖动时整张图反复重绘，已移除；入场只对内层做 opacity 渐显，规则写进 `canvas.css` 注释 |
| 文档切换时的「适应画面」与测试设置视口赛跑，会让测量偶发落到 0.3 倍全览 | 用例等待取景落定后再设视口；产品侧适应画面只在打开/切换文档时执行 |
| 视口外元素 | `onlyRenderVisibleElements` 保持开启，局部编辑成本与可见元素数线性相关 |
| 参考线 | `canvasStore.setGuides` 等值守卫，避免每帧空重渲染（沿用） |

## 5. 已知边界

- 全览拖拽每步仍约 137ms：React Flow 受控模式下每次 `onNodesChange` 都会把完整 `nodes` 数组交回，内部 `adoptUserNodes` 对 500 个节点全量处理。进一步优化需改为非受控模式或拖动期间只更新被拖节点，属于架构级改动，本次未做。
- 软件渲染 + Trace 开销下的绝对值偏大；有 GPU 的真实浏览器会更快，前后对比结论不受影响。
- dev 模式（StrictMode 双渲染）数值约为生产构建的 2 倍，生产构建是性能口径。
